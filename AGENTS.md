
# ModernApp v2 workspace instructions

Use these instructions when IBM Bob or another AI assistant works in a ModernApp v2 workspace created by the Embedded App Connector extension.

## Goal

Safely update ModernApp v2 app files while preserving compatibility with the extension's pull, preview, lock, and push workflow.

## App folder detection

- A folder is a ModernApp v2 app when it contains `embeddedapp.config.json`.
- **MANDATORY BEFORE-EDIT GATE:** Before editing any file, find all app folders under the workspace root by locating `embeddedapp.config.json` files and determine the target app folder.
- If exactly one app folder exists, or the user explicitly identifies an app folder by name or path, use that folder.
- If multiple app folders exist and the user's request does not explicitly identify one, **STOP and ask the user which app folder to modify. Do not edit any files until the user answers.**
- Do not infer the target app from the current working directory, the currently open file, the nearest folder, or the first search result.
- Keep changes scoped to the selected app folder unless the user explicitly asks for workspace-wide changes.

## Duplicate / ambiguous BYODM table gate (MANDATORY)

- Before constructing any SQL, choosing any query, or creating/updating/scaffolding any app that reads or writes a BYODM table, look up the requested table name in the BYODM master index.
- **If the same table name exists in more than one schema (for example `emp` in `[HR].[emp]` and `[Payroll].[emp]`), STOP immediately.** Present every matching option as `[schema].[table]` and ask the user which one to use.
- Do NOT pick a schema yourself, do NOT proceed with more than one matching table, and do NOT build, scaffold, write, or edit any app code or query until the user replies with a single `[schema].[table]`.
- Presenting the options is not enough. You must stop and wait for the user's answer before doing anything else. Suggesting or building against two same-named tables from different schemas is a workflow failure.
- This gate applies to EVERY flow: creating a new app, editing an existing app, and constructing a standalone query.
- Only after the user selects one `[schema].[table]` may you read that schema's detail file and continue building.

## Files to avoid editing

Do not edit these generated or extension-managed files unless the user explicitly asks:

- `embeddedapp.config.json` links the local folder to the platform app.
- `embeddedapp.dev.json` contains local runtime credentials and should never be committed.
- `embeddedapp.d.ts` is generated SDK/type guidance.
- `embeddedapp-dev.js` is generated local-preview support.
- `jsconfig.json` is generated editor configuration.
- `byodmtablemetadata.*.json` are generated BYODM table metadata master index files.
- `.byodm/` directory contains generated schema detail files.
- Root `AGENTS.md` is workspace guidance managed by the extension.

## Deployable files

- Only `.html`, `.css`, and `.js` files are pushed to the platform.
- Do not create `.json`, `.txt`, image, or other asset files expecting them to deploy unless the user explicitly accepts that they are local-only.

## SDK-first approach

- Start by reading `embeddedapp.d.ts` in the selected app folder.
- Prefer `EmbeddedApp` SDK APIs when they fit the task.
- For DB/Streamlit query data, do not invent query names. First read the selected app folder's `embeddedapp.dev.json`, then read the matching workspace-root Streamlit query metadata file for that app environment:
  - Dev: `streamlitqueries.dev.json`
  - UAT: `streamlitqueries.uat.json`
  - Production: `streamlitqueries.prod.json`
  - Local: `streamlitqueries.local.json`
- Before using any Streamlit query metadata, verify it belongs to the selected app's environment and client:
  1. Read the file's root `_metadata` object and query list from `queries`.
  2. Compare the app's `embeddedapp.dev.json.apiUrl` with `_metadata.apiUrl` or `_metadata.apiUrlNormalized`.
  3. Compare the app's `embeddedapp.dev.json.clientGUID` / `clientName` with `_metadata.clientGUID` / `_metadata.clientId` / `_metadata.clientName` when present.
  4. If the metadata file is missing, has no `_metadata`, has no client/API metadata, or does not match the app's `apiUrl` and client, do not pick a query from it. Ask the user to reconnect the Embedded App Connector to the correct client/environment and pull or refresh the app so the connector downloads the correct `streamlitqueries.json` metadata, then retry after the file is updated.
- Use matching Streamlit query metadata to suggest queries by reviewing fields in this order:
  1. `QueryDescription`
  2. `TableDescription`
  3. table names from `TableDescription` keys for BYODM DataBase
  4. `QueryName`
  5. `QueryText`
- If multiple Streamlit queries look relevant, present the matching query options to the user and include a `None of these` option. Do not proceed with an ambiguous query choice.
- **Cross-schema disambiguation:** When a Streamlit query matches by table name, also check the BYODM master index to see if the same table name exists in other schemas. If it does, present the existing Streamlit query with its full `[schema].[tablename]` context AND a `None of these` option so the user can request a query for the other schema's table instead. Do not silently assume the existing query is the correct match.
- After the correct query is selected, use its `QueryName` with `EmbeddedApp.callAutoBPAsJSON(...)` for reads or `EmbeddedApp.callReadWriteObject(...)` for writes.
- Respect units documented in `embeddedapp.d.ts`; do not infer seconds vs milliseconds from parameter names alone.
- Before using Factory.ai/Droid APIs with a model argument, call `EmbeddedApp.getFactoryAIModels()` and pass one of the returned `Value` strings.
- If no SDK capability fits, use a small app-local implementation. Use external libraries only when already present or explicitly requested.

## Locks and safety

- Respect files that are locked or read-only. Do not force-write locked files.
- Preserve the existing HTML, CSS, and JavaScript structure unless the task requires changing it.
- Avoid broad rewrites. Make the smallest safe change that satisfies the user request.

## BYODM table metadata for SQL query construction

When the user asks you to construct SQL queries against BYODM database tables, use the BYODM table metadata files instead of guessing table or column names.

### Recognizing BYODM database requests

The BYODM (Bring Your Own Data Model) database is the only database accessible through the Modern App platform. When a user mentions any of the following, treat it as a BYODM database query request:

- "BYODM db", "BYODM database", "BYODM tables"
- "the database", "our database", "platform database"
- "insert into [table name]", "update [table name]", "query [table name]"
- "write a SQL query", "construct a query"
- Any request involving table names, column names, or SQL operations (INSERT, UPDATE, SELECT, JOIN)

If the user does not explicitly mention any database or data source but asks for a query, insert, update, or any SQL operation involving tables and columns, default to the BYODM database. Do not ask the user which database they mean, there is only one.

**You MUST always check the BYODM metadata files when no matching Streamlit query is found.** Do not skip this step. Do not tell the user you cannot help with database queries. Do not guess table or column names. Always read the BYODM metadata files first, then construct the query from the actual metadata.

If the user's request is ambiguous and could refer to either Streamlit queries or BYODM tables, check Streamlit queries first (per the workflow below). Only fall back to BYODM metadata if no Streamlit query fits.

### When to ask the user for clarification

If you searched the BYODM metadata files but cannot find the tables or columns the user is referring to, do not guess or proceed with incomplete information. Ask the user clarifying questions such as:

- "Which schema is the table in? I found these schemas: [list schema names from master index]"
- "I could not find a table named '[name]'. Did you mean one of these? [list closest matching table names]"
- "Which columns do you want to insert/update? Here are the columns I found in [table]: [list column names]"
- "Can you provide the exact table name or describe what data it stores?"
- "Are you referring to a different environment? The current metadata is for [environment name]."

Always provide the options you found in the metadata so the user can pick from actual table/column names. Do not ask open-ended questions when you can provide concrete options from the metadata files.

### File structure

- **Master index**: `byodmtablemetadata.{env}.json` at workspace root (one per environment: dev, uat, prod, local)
- **Schema detail files**: `.byodm/{env}/{schemaName}.json` (hidden subfolder, one file per BYODM schema)

The `dbo` schema is excluded from all metadata files. Both file types contain a `_m` block with self-documenting legends (`_s`, `_r`, `_t`, `_c`, `_i`) that describe the format of each section. Read the `_m` block first to understand the structure.

### Bob's SQL construction workflow

**MANDATORY SQL RESPONSE CONTRACT:** Whenever you construct or recommend a new query, your response to the user MUST include all three fields below. Do not provide only the SQL, and do not finish the response if any field is missing.

1. **`QueryName`**: A concise, meaningful, and unique name that indicates the query's operation and target.
2. **`QueryText`**: The complete SQL statement, including the correct schema-qualified table names and parameter placeholders.
3. **`QueryDescription`**: A meaningful description that states the operation, target table(s), important filters or joins, and intended result.

Before sending the response, explicitly verify that `QueryName`, `QueryText`, and `QueryDescription` are all present and non-empty.

1. **Try Streamlit queries first.** Before constructing any SQL from BYODM metadata, check the matching `streamlitqueries.<env>.json` file for an existing query that fits the user's need. Use the SDK-first approach described above.
2. **Fall back to BYODM metadata when no Streamlit query fits.** If no existing Streamlit query can serve the user's request, you MUST read the BYODM table metadata files to construct a new SQL query. Do not skip this step. Do not tell the user you cannot help. Do not guess table or column names. Always read the metadata files first.
3. **Check the query format from the Streamlit query JSON file before constructing.** Read an existing query from `streamlitqueries.<env>.json` to understand the expected SQL format (parameterization style, naming conventions, structure). Match that format in the query you construct.
4. **Only SELECT, INSERT, and UPDATE statements are allowed.** Do not construct DDL statements (CREATE, ALTER, DROP, TRUNCATE, etc.) or DELETE statements. If the user requests a DDL or DELETE operation, explain that only SELECT, INSERT, and UPDATE queries are supported and ask them to perform DDL/DELETE operations through the platform's database administration tools.
5. Read the master index (`byodmtablemetadata.{env}.json`) that matches the app's environment (check `embeddedapp.dev.json` for the API URL, then match it against the master index `_m.a` field).
6. Use the `_m.sf` (schemaFiles) map in the master index to discover which schema detail files exist and their paths. Do not guess file paths. The `sf` map gives the exact path for each schema's detail file (e.g., `{ "Sales": ".byodm/dev/Sales.json" }`).
7. Search the master index `s` section for relevant tables by table name or column name (column names are in the `c` array per table). When table descriptions (`d` field) are present, use them too. **If you cannot find the table or columns the user mentioned, do not guess. Ask the user clarifying questions using the options you found in the metadata (see "When to ask the user for clarification" above).** **If the same table name exists in multiple schemas, STOP and ask the user which schema's table to use. Present the options as `[schema].[tablename]` and do not proceed until the user picks one.**
8. Check the `r` array (relationships) for foreign key JOIN paths. Each entry is `[constraintName, fromSchema, fromTable, fromColumn, toSchema, toTable, toColumn]`.
9. Read the schema detail files (use the paths from `_m.sf`) for the schemas containing the tables you need. These files contain full column metadata: data types, nullability, primary key flags, auto-increment flags, foreign key references, column descriptions, and index information.
10. Construct the SQL query using the column metadata:
    - Use schema-qualified table names: `[schema].[tablename]` (e.g., `INSERT INTO [Sales].[Orders](Name, Amount) VALUES(?, ?)`)
    - Use `?` positional placeholders for parameters (matching the existing Streamlit query format)
    - **Two paths for INSERT/UPDATE depending on the SDK method:**
      - **`callAutoBPAsJSON`**: Executes SQL directly. Use `INSERT INTO [schema].[tablename](col1, col2) VALUES(?, ?)` with `?` positional placeholders for user input.
      - **`callReadWriteObject`**: Backend parses a SELECT statement to identify the target table and columns, then handles INSERT/UPDATE internally. The SELECT must be a simple single-table query: `SELECT * FROM [schema].[tablename]`. Do NOT include JOINs in the SELECT for `callReadWriteObject` because the backend cannot identify which table to target when multiple tables are joined.
    - SELECT queries used with `callAutoBPAsJSON` for reading may use JOINs across tables using FK relationships from the `r` array
    - Use correct data types for WHERE clause formatting (quote strings, use date literals for DATE columns, etc.)
    - Use index information to suggest optimized WHERE/JOIN clauses on indexed columns
    - Use FK references for correct JOIN ON clauses
    - Skip auto-increment (`ai:1`) columns in INSERT statements
    - Use nullable flag to decide on IS NULL / LEFT JOIN vs INNER JOIN
11. Present the query to the user for review using three explicitly labeled fields: **`QueryName`**, **`QueryText`**, and **`QueryDescription`**. All three fields are mandatory. `QueryDescription` must clearly describe what the query does, which table(s) it targets, its important filters or joins, and what operation it performs. This description is stored in `streamlitqueries.<env>.json` and is the primary field AI assistants use to discover existing queries in the future. A good description ensures the next AI search finds this query without needing to construct a new one. Examples:
    - `"Insert a new order record into [Sales].[Orders] with Name, Amount, and Status columns"`
    - `"Select all active orders from [Sales].[Orders] joined with [Sales].[Customers] on CustomerId"`
    - `"CRUD query for [Sales].[Orders] table - supports SELECT, INSERT, and UPDATE operations"`
12. After user approval, tell the user to save the query using the Modern App Query UI from the platform. When saving, the user should enter the `QueryName` and the `QueryDescription` you generated. Once saved, the query will appear in the matching `streamlitqueries.<env>.json` file. If query will not appear in `streamlitqueries.<env>.json` use extension Refresh Streamlit Query Action from sidebar, and can then be used in app code.
13. **Use a dynamic query name when GET, INSERT, and UPDATE share the same base query.** If the user needs to read, insert, and update the same table with the same base query logic, do not create three separate queries. Instead, suggest a single query with a dynamic query name (e.g., `Sales_Orders_CRUD`) that handles all three operations through conditional logic or parameters. This reduces the number of queries to manage and keeps the query set clean.

### Using BYODM queries in app code

After the user saves the constructed SQL query on the platform and it appears in `streamlitqueries.<env>.json`, use the `QueryName` with the EmbeddedApp SDK:

```js
// SELECT - read rows with callAutoBPAsJSON (JOINs allowed in the SQL)
const rows = await EmbeddedApp.callAutoBPAsJSON('GetOrders', ['Active']);

// INSERT via callAutoBPAsJSON - direct SQL execution with ? positional parameters
// SQL: INSERT INTO [Sales].[Orders](Name, Amount) VALUES(?, ?)
await EmbeddedApp.callAutoBPAsJSON('InsertOrder', ['Widget', 99.95]);

// INSERT/UPDATE via callReadWriteObject - backend identifies table from a simple SELECT
// SQL must be: SELECT * FROM [Sales].[Orders] (NO JOINs)
await EmbeddedApp.callReadWriteObject('SaveOrders', {}, [], {
    newRows: [{ Name: 'Widget', Amount: 99.95 }],
    updatedRows: [{ Id: 1, Name: 'Updated Widget', Amount: 129.95 }]
});
```

### What to avoid

- Do not edit `byodmtablemetadata.*.json` or `.byodm/` files. They are generated by the extension.
- Do not construct SQL queries from guessed table or column names. Always verify against the metadata files.
- Do not skip reading the BYODM metadata files when no Streamlit query is found. You MUST read the metadata files before constructing any SQL.
- Do not tell the user you cannot help with database queries. Always check the metadata files first.
- Do not guess or proceed with incomplete table/column information. Ask clarifying questions with concrete options from the metadata.
- Do not construct DDL statements (CREATE, ALTER, DROP, TRUNCATE) or DELETE statements. Only SELECT, INSERT, and UPDATE queries are supported.
- Do not construct BYODM SQL queries without first checking the `streamlitqueries.<env>.json` file for an existing query that fits the user's need.
- Do not construct BYODM SQL queries without first reading an existing query from `streamlitqueries.<env>.json` to match the expected query format.
- Do not use unqualified table names in SQL. Always use `[schema].[tablename]` notation (e.g., `[Sales].[Orders]`, not just `Orders`).
- Do not include JOINs in SELECT statements used with `callReadWriteObject`. The backend needs a simple `SELECT * FROM [schema].[tablename]` to identify the target table for INSERT/UPDATE operations. JOINs prevent table identification.
- Do not use `callReadWriteObject` with INSERT SQL statements. Use `callAutoBPAsJSON` for direct INSERT execution, or use `callReadWriteObject` with a simple SELECT and pass rows via `newRows`/`updatedRows`.
- Do not guess schema detail file paths. Use the `_m.sf` map from the master index to find the exact paths.
- Do not assume which schema a table belongs to when the same table name exists in multiple schemas. STOP, present all matching `[schema].[tablename]` options, and ask the user to choose before constructing the query.
- If the metadata files are missing or stale, ask the user to reconnect the Embedded App Connector to refresh them.
